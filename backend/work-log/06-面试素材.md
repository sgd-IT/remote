## 告警列表慢查询诊断与 N+1 批量改造 · 2026-10-20
> 项目：消防远程值守系统｜角色：独立负责
- **技术维度**：后端深度（排查 / 性能）
- **场景与规模**：移动端告警中心列表加载慢；单租户（养老院）告警 1.4 万条占全表 15,779 条的 91%，其中 94% 待处理；接口 GET /eiot/firewatch/alarm-order/page
- **我做了什么**：按"前端接口 → 后端方法 → 线上索引/数据分布取证 → EXPLAIN → 组装段审查"五步定位；确认 SQL 命中索引且无 filesort 后，把主因修正到组装循环内的 N+1（每条 4 次单查、每页约 80 次），设计三级串行批量改造（deviceId→设备 Map→productKey→产品 Map→categoryId→分类 Map→内存回填）
- **难点与解决**：首轮判断"索引列序不优"被实测推翻 → deleted 全为 0 时列序收益趋零、生产 DDL 纯风险 → 撤回索引变更只改应用层；评审时拦下三处静默故障：toMap 重复 key 抛异常、null value 抛 NPE、selectBatchIds 传业务键按主键查空导致类型列全空
- **结果**：主因定性从数据库层修正到应用层；批量方案每页查询约 80 次降到 3~4 次（用户实施中，未跑通验证）；避免一次无收益的生产索引 DDL
- **追问与答案**：① 为什么一开始怀疑索引？→ 1.4 万条 + 单租户集中 + 历史上建议过加索引，先验证最便宜的假设；② EXPLAIN 里看什么判断不用改索引？→ type=ref 说明命中、Extra 无 Using filesort 说明排序由索引承担，rows 偏大是数据倾斜不是列序问题；③ 为什么 selectBatchIds 传 productKey 不报错？→ MP 拼 WHERE id IN ('业务键')，MySQL 隐式转 0，静默查空，页面表现为类型列全空
- **技能**：Java / MySQL / EXPLAIN 执行计划 / 性能优化 / MyBatis-Plus

## 园区监管平台 OpenAPI 对接层 · 2026-10-20
> 项目：hc-standard｜角色：独立负责
- **技术维度**：设计模式 / 逻辑设计
- **场景与规模**：本地安全生产平台作为被监管方，需按园区 20+ 类上报资源（作业票、风险单元、承包商、值班值守）对接；OpenAPI 客户端 24 个、platement 包 91 个类、8 类特殊作业票型
- **我做了什么**：拆两层——基类管传输与判定（HMAC-SHA256 签名、requireSuccess 业务码判定、createdId 兼容 data 两种形态、批量 10 条分批且任一批失败即返回），子类只管白名单报文（非平台字段清理、按票型移除非法 level、operatorInfo 分隔符转换、子表按文档字段重建）
- **难点与解决**：实体直接序列化带上前端展示字段与子表对象 → 平台严格 schema 返回 500 → 改为按平台文档白名单重建报文；内部 operatorInfo 用逗号同时分隔"人"和"人内字段"存在歧义 → 靠"逗号后是否纯中文+冒号"识别人员边界，转成平台分号分隔
- **结果**：20+ 类上报资源接入；8 类票型推送链路打通；93 项契约校验器（777 行）作为可开关的本地预校验
- **追问与答案**：① 为什么不用 @JsonIgnore 隐藏字段？→ 同一实体既要给前端又要给平台，且不同接口字段集不同，注解只能静态裁一套，白名单重建更可控；② 为什么批量是 10 条？→ 平台批量接口有条数上限，超限直接报错，分批还能定位失败批次；③ HTTP 200 为什么还要判 code？→ 平台业务失败也回 200，只看 HTTP 状态会把失败当成功写库
- **技能**：Java / OpenAPI 集成 / 设计模式 / 架构设计

## 上报同步三态状态机与定时补偿 · 2026-10-20
> 项目：hc-standard｜角色：独立负责
- **技术维度**：逻辑设计 / 并发
- **场景与规模**：3 类基础资料上报（第三方单位/装置开停车/大检修）+ 8 类业务对象定时同步；园区平台无幂等键，超时后无法确认对方是否落库
- **我做了什么**：抽模板骨架固定公共流程、差异走子类钩子；同步状态分三态（成功/失败/结果不明），用 uncertain 标记在调用前置位、平台明确失败时复位；入口 claim 乐观占位（UPDATE 命中 1 行才继续）；删除走软删保留追溯；定时任务双 cron 扫未同步 ID 批量补推
- **难点与解决**：超时被当失败重试 → 平台出现重复记录 → 把"结果不明"独立成态，禁止自动重试、只能人工对账；用户连点两次 → 两次都读到未同步 → 用条件更新占位，第二个请求直接被拒
- **结果**：3 个上报资源共用一套骨架；8 类同步对象纳入补偿；重复上报与并发提交在入口拦住
- **追问与答案**：① 为什么不用分布式锁？→ 单实例部署，锁的粒度就是单条记录，DB 条件更新足够，引入 Redis 锁只会增加故障面；② claim 失败怎么提示？→ 统一提示"记录不存在、正在处理或结果待核实"，不暴露内部状态；③ 定时任务为什么吞异常？→ 一个模块失败不能阻断其他模块，日志留痕后靠下一轮补偿收敛
- **技能**：Java / 状态机设计 / MySQL / Spring 定时任务

## 8 类票型的配置驱动建模 · 2026-10-20

## 时间口径分离与调度粒度拆分 · 2026-10-20
> 项目：hc-standard｜角色：独立负责
- **技术维度**：逻辑设计
- **场景与规模**：天/月/年周期排查任务派送；风险单元按计划停机时间自动启停，涉及 8 类对象的平台推送
- **我做了什么**：派送时刻改为"目标日 + 配置的作业开始时间"，plan_time 逾期基准保持当日 00:00 不变；风险单元新增每分钟只做本地状态切换的任务，原 23:30/06:00 含平台推送的同步任务频率不动；停机记录写入改为条件生效（stopTime <= now）；状态切换固定"先联动排查任务、再更新单元"
- **难点与解决**：一个时间字段同时当派送时刻和逾期基准 → 改一个坏另一个 → 拆成两个口径；整体提频会把平台调用量成倍放大 → 按"是否调外部"拆任务，只提本地任务的频率
- **结果**：派送时间与逾期统计解耦；本地状态分钟级对齐，平台调用量不变；中断后下一轮调度自愈
- **追问与答案**：① 为什么不用延迟队列/MQ？→ 引入中间件与运维成本，需求只要分钟级，收益不匹配；② 先任务后单元为什么不能反？→ 单元状态是任务的判据，先改单元会让任务联动失去依据；③ 每分钟扫全表吗？→ 按停机时间窗口走索引只取到期/过期记录，扫描量与存量无关
- **技能**：Java / Spring 定时任务 / 逻辑设计 / 业务建模

## 隐患治理九态闭环状态机 · 2026-10-20
> 项目：hc-standard｜角色：独立负责
- **技术维度**：逻辑设计
- **场景与规模**：隐患从上报到闭环 9 种操作、7 个状态节点，涉及上报人/责任人/审核人三类角色；单个方法 140 行承载全部流转
- **我做了什么**：单入口 operationType 驱动，每个操作带前置状态白名单（认领只允许 0/9、申请关闭只允许 21、确认关闭只允许 30）；curOperatorId 当待办人指针兼权限判据，进入先校验、流转时按操作重写；日志 + 站内消息 + 平台推送（businessState 1/2/4）三联动，推送失败降级到补推
- **难点与解决**：状态和"该谁处理"分两处维护会卡单或越权 → 把待办人指针纳入状态机；外部推送失败不能回滚用户已做的流转 → try-catch 留痕 + 补推兜底
- **结果**：9 种操作收敛一个入口；越权在入口被拦；复盘时定位到延期重复申请校验读错对象的缺陷

- **技能**：Java / 状态机设计 / 业务建模
