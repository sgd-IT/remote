## 列表接口租户名回填的 N+1 体检 · 2026-10-20
> 项目：消防远程值守系统
### 【类型】
性能优化 / 技术债
### 【背景】
上一轮修完告警列表的 N+1 后回扫同类写法，发现设备、空间、摄像头、远程控制台四条列表链路都在做同一件事：把租户 ID 去重后，循环里逐个 `tenantService.getTenant(id)` 取企业名。注释都写着“避免 N+1 查询”，实际只是把“按行查”降成了“按租户查”——页内企业不重复时一页仍是十几次单表查询；摄像头树与远程控制台是把全量数据按企业分组，企业越多查得越多。
### 【方案】
1. 模式识别：判断标准不是“有没有循环”，而是“循环体内有没有数据库往返”；去重只压低了系数，查询次数仍是 O(去重后条数)。
2. 用现成能力收敛：TenantService 已有 `getTenantMap(Collection<Long>)`（内部 selectBatchIds，一条 IN 查询），同仓 UserController 的分页与导出早就在用；四条链路统一改成“收集 tenantIds → 一次 getTenantMap → 内存回填”。
3. 租户上下文：跨租户取名要包 `TenantUtils.executeIgnoreWithResult`，与原来的 executeIgnore 语义一致，否则系统租户查不到企业数据。
4. 容错取舍：原来的 try-catch 是逐条吞异常；改批量后不再吞——租户名只是展示字段，但批量查询走的是同一个库，真出异常时主列表本来也查不出来，继续吞只会把问题藏起来。
### 【我的角色】
参与：同类模式全仓体检 + 定位 5 处同构实现 + 给出统一改法并落地
### 【结果】
同一套模板在 5 处（DeviceInfoController、AppDeviceInfoController、FireSpaceController、VideoCameraController、RemoteConsoleServiceImpl）收敛为“一次 IN 查询 + 内存回填”，企业名回填的查询次数从“页内租户数”降为 1；顺带列出了剩余同类点（FirePatrolTaskServiceImpl 循环 selectById、DeviceFunctionServiceImpl 循环 selectById、VideoCameraServiceImpl 批量创建循环查重+插入），交由用户后续处理。
### 【踩坑 & 根因】
① 注释写着“避免 N+1”不等于真避免了——去重后仍在循环里查库，只是把 N 次变成去重后的 N 次，单租户数据下看起来完全正常；② 同一段模板被复制到 4 个 Controller/Service，改一处不会带动其他处，靠看注释根本发现不了，只能按“循环体内有没有 DB 调用”扫代码。
### 【可复用结论】
判断 N+1 只看一条：循环体内有没有数据库会话往返，有就一律批量；“先 distinct 再循环查”只是缩小系数，不是修复；批量回填的验收标准是调用次数 N→1，不是方法名带 Batch，也不是注释写了“避免 N+1”。
### 【关联】
code：DeviceInfoController#getDeviceInfoPage、AppDeviceInfoController#getDeviceInfoPage、FireSpaceController#listFireSpace、VideoCameraController#getCameraTree、RemoteConsoleServiceImpl#getDeviceTree、TenantService#getTenantMap
### 【标签】
后端 / 性能优化 / Java / 设备

## 告警列表慢查询诊断与 N+1 批量改造 · 2026-10-20
> 项目：消防远程值守系统
### 【类型】
性能优化 / 故障排查
### 【背景】
移动端告警中心列表加载慢。单租户（养老院）告警量 1.4 万条，占全表 15,779 条的 91%，其中 94% 长期停留在待处理状态。用户判断"数据量不大却很慢"，首要怀疑数据库索引。
### 【方案】
解决步骤（按执行顺序）：
1. 前端定位：移动端 alarm-center 页面调 GET /eiot/firewatch/alarm-order/page；
2. 后端定位：FireAlarmOrderServiceImpl.doPageFromAlertRecord 分两段——selectPage 查库段 + 返回组装段，改造只动后者；
3. 线上取证：prod MCP 执行 SHOW INDEX 确认 idx_tenant_alert_time (tenant_id, alert_time, deleted) 已存在；按租户统计确认 174 租户占 91%；
4. EXPLAIN 验证：type=ref、Extra 无 Using filesort → 排序由索引天然承担，判定索引够用，撤回首轮"改列序为 (tenant_id, deleted, alert_time)"的建议，不做生产 DDL；
5. 锁定根因：组装循环内每条记录 4 次单查——fillDeviceType（设备→产品→分类）+ tenantApi.getTenantName，每页 20 条约 80 次额外查询；
6. 框架盘点：BaseMapperX 提供 selectList(SFunction, Collection) 与 selectByIds 批量能力；TenantApiImpl → tenantMapper.selectById 无缓存，每次都是真实查库；
7. 改造设计：三级串行批量——deviceId 去重→设备 Map→提取 productKey→产品 Map→提取 categoryId→分类 Map→最后一遍纯内存回填；租户名 distinct 后逐个查（一页通常 1~2 个）；
8. 逐轮代码评审：拦截三处隐患——Collectors.toMap 重复 key 抛 IllegalStateException（同租户一页必炸）、value 为 null 抛 NPE（getTenantName 异常返回 null）、selectBatchIds 误用于业务键 productKey（按主键查字符串，静默查空致类型列全空）。
### 【我的角色】
独立负责：prod 线上取证 + 根因定位 + 改造方案设计 + 逐轮代码评审
### 【结果】
主因定性从"缺索引"修正为应用层 N+1；批量方案预期每页查询从约 80 次降到 3~4 次；撤回索引变更避免了一次无收益的生产 DDL 风险。代码由用户自行实施，截至记录时改造未跑通验证。
### 【踩坑 & 根因】
① 首轮把索引列序当问题 → 实测 EXPLAIN 无 filesort、单租户 deleted 全为 0 → 列序收益趋零，生产改索引纯风险；② 逐条改批量时方法名改了但调用点没改（循环内 Collections.singletonList 逐条调）→ N+1 原样保留；③ selectBatchIds 只按主键批量，传业务键 productKey 时 MySQL 隐式转换静默查空 → 批量方法选错等于数据静默丢失。
### 【可复用结论】
"数据不多却很慢"先拆"查库段 vs 组装段"，组装段循环内逐条查询是最常见根因；批量改造的验收标准不是方法名带 Batch，而是调用次数真的从 N 降到 1——循环内删调用、循环外统一调一次；MyBatis-Plus 的 selectBatchIds 只认主键，按业务键批量必须用 selectList(字段, 集合)；Collectors.toMap 默认禁止重复 key 和 null value，收集前先 distinct，value 可能为 null 时改 HashMap 手动 put。
### 【关联】
code：FireAlarmOrderServiceImpl#doPageFromAlertRecord、fillDeviceTypeBatch；db：eiot_alert_record（idx_tenant_alert_time）；线上取证：prod MCP SHOW INDEX / EXPLAIN / 租户分布统计
### 【标签】
后端 / MySQL / 性能优化 / 告警

## 自动排班锚点轮换 · 2026-10-19
> 项目：消防远程值守系统
### 【类型】
逻辑设计 / 功能开发
### 【背景】
24 小时值班制要求每天 1 条全天班（08:00 → 次日 08:00），值班人员按名单轮换。原实现用"当月第几天"对人数取模，31 天月份的次月 1 号会连排同一人（31 % 2 = 1，1 % 2 = 1）；同时每天一次 selectCount 判断是否已有排班，重复执行会重复生成。
### 【方案】
- 轮换基准改为绝对天数 epochDay，与月份天数解耦；
- 锚点轮换：取该单位"日期最大的一条全天班"（含未来月份）作为锚点，`floorMod(anchorIndex + (date - anchorDate), size)` 全局推算，先排哪个月结果都一致；
- 锚点人已不在本次名单（调岗、导入没填用户 ID）时锚点作废，从名单第 1 位重新起头；
- 名单 `distinct` 保序去重：重复 ID 会让轮换序列错位，同一人被连排；
- 已有排班按日期区间一次查出 Set，循环内跳过，替代原来的每日一次 count 查询；
- 只排明天及以后（今天和过去不生成），排未来月份时从月初开始。
### 【我的角色】
独立负责：规则设计 + 实现 + 边界验证
### 【结果】
单条改动 +66/-36；月边界连排消除；重复执行幂等（已有日期不重复生成）；排班查询从 N 次（每天一次 count）降为 2 次（锚点 + 已有日期）；2 人隔日交替、3 人上 1 休 2 均验证通过。
### 【踩坑 & 根因】
① 取模基准用"当月第几天"→ 每月天数不同，跨月必然错位 → 周期性轮换的基准必须是绝对时间；② 锚点不能取"最后插入的一条"→ 先排未来月份再排当月时，锚点会指向未来，导致序列回跳 → 必须取"日期最大"；③ 名单不去重 → 重复 ID 占两个位置，轮换序列整体偏移。
### 【可复用结论】
周期性轮换的取模基准要用绝对时间（epochDay），不要用"当期第几个"；需要"先算哪一段结果都一致"时，用持久化锚点 + 日期差取模，而不是每次从起点重数；批量生成前先把"已存在的日期"一次查成 Set，避免循环内查库。
### 【关联】
code：FireDutyScheduleServiceImpl#autoSchedule；db：fire_duty_schedule（property_id + shift_type + schedule_date）；git：ed8108b（锚点轮换+跳过已有）、9ffa7a2（前端轮换顺序）、a01ea76（24 小时制改造）
### 【标签】
后端 / Java / 逻辑设计 / 值守

## 告警去重时间戳竞态 · 2026-10-14
> 项目：消防远程值守系统
### 【类型】
故障排查 / 技术债
### 【背景】
告警统一落库前按 dedupKey（deviceId:alarmType:sourceType）做 5 分钟窗口去重。持续告警（设备反复上报同一事件）在窗口边界出现时间戳被刷新、判重失准的问题；同时代码里并存两套判断：putIfAbsent 组合和基于 get + remove 的 isDuplicate 方法。
### 【方案】
- 用 `ConcurrentHashMap.putIfAbsent(key, now)` 原子占位：同 key 并发只有一个线程拿到 null（首次）；
- 把时间戳刷新收敛进"判定为非重复"分支，用三参 `replace(key, old, now)` 做 CAS 刷新；
- 删除基于 get + remove 的 `isDuplicate` 方法，判定只保留一套。
### 【我的角色】
独立负责：根因定位 + 修复 + 并发边界复核
### 【结果】
单文件 +2/-18；判定逻辑从两套收敛为一套；窗口内重复告警不再入库。
### 【踩坑 & 根因】
① `get` 判断再 `put` 是两步操作，中间存在竞态，必须用 putIfAbsent 原子占位；② `replace` 的返回值没校验——两个线程同时读到过期时间戳时都会通过窗口检查，CAS 只有一个成功，另一个仍会继续落库，当前去重是"尽力而为"而非强一致；③ 同一件事留两套判断，后改的一处迟早与另一处打架。
### 【可复用结论】
缓存去重要"原子占位 + CAS 刷新"一体，不要先 get 再判断；CAS 失败要当重复处理（`if (!replace(...)) return null`），否则窗口边界会漏；内存缓存只做第一层，强一致要 DB 唯一索引或分布式锁兜底。
### 【关联】
code：AlarmRecordService#saveAlarm、buildDedupKey；git：f3dfa8e
### 【标签】
后端 / 并发 / 缓存 / 告警

## UDP 设备在线状态判定重构 · 2026-09-08
> 项目：消防远程值守系统
### 【类型】
架构 / 技术债
### 【背景】
UDP 组件自己维护内存会话表 `lastSeen`（ConcurrentHashMap）+ Vert.x `setPeriodic(30s)` 清理，60 秒无上报即判离线。但大华终端 1 小时才上报一次，任何秒级/分钟级超时都会误判；同时 `DeviceStateCheckTask` 也按产品 keep_alive_time 判定离线，形成两套状态源。
### 【方案】
- 删除 `UdpComponent.lastSeen`、`handleOffline`、`UdpVerticle.cleanOffline` 及周期任务；
- 在线状态统一由产品 `keep_alive_time` 驱动（大华当前 7200s = 2 轮上报）；
- 各协议组件按自身心跳周期设阈值（YWN 6 分钟、GB/T 26875 60 秒、四信 600/900 秒），但"判离线"的动作只保留一处。
### 【我的角色】
独立负责：方案设计 + 三端组件核对 + 删除旧逻辑
### 【结果】
UDP 组件净删 62 行；消除内存态与持久态双份状态源；误判离线消除；协议组件职责收敛为"收报文 + 记录活跃时间"。
### 【踩坑 & 根因】
① 内存会话表随进程重启丢失，与 DB 状态不一致；② 超时阈值不能拍脑袋，必须由设备上报周期推导（≥ 2 个周期，留一轮容错）；③ `ConcurrentHashMap.forEach` 中直接 remove 会破坏遍历，需先收集再删（旧代码写法正确，但整段被一并移除）。
### 【可复用结论】
设备在线状态只保留一个判定源；阈值 = 上报周期 × 2；协议组件只负责收报文和置时间戳，离线判定交给统一任务；能删的内存状态就删，双份状态源迟早不一致。
### 【关联】
code：UdpComponent、UdpVerticle、DeviceStateCheckTask；git：e2e72e2

## 告警工单状态解析器 · 2026-08-19
> 项目：消防远程值守系统
### 【类型】
架构 / 技术债
### 【背景】
告警工单状态同时存在三个来源：handle_status（0/1/2/3）、details 文本处置记录、readFlg 已读标记。前端列表、统计、导出各算各的，同一单在不同页面状态不一致。历史数据让问题更复杂：老单没有 handle_status，只能从 details 文本推断。
### 【方案】
- 抽 `AlertOrderStatusResolver`，定义三级优先级：handle_status（权威字段）> details 末段 `[` 处置记录 > readFlg 兜底；
- 同一口径输出两份：Java 方法（单条解析）+ `ORDER_STATUS_CASE_SQL` 常量（分页筛选/批量统计的 SQL CASE），列表与统计同源；
- details 用 `lastIndexOf('[')` 取最后一条处置记录，而不是全文 contains，避免早期记录命中；
- 后续演进：handle_status=3 时若末段含"关闭工单"返回 closed，继续与 SQL 口径对齐。
### 【我的角色】
独立负责：口径定义 + 双实现 + 调用点迁移
### 【结果】
新增 70 行工具类；分页筛选用 `ORDER_STATUS_CASE_SQL + " = {0}"` 直接拼 SQL；状态口径从多页面各算收敛为单点维护。
### 【踩坑 & 根因】
① 用文本记录当状态来源是数据债，只能"末段匹配 + 优先级兜底"，不能全文匹配；② Java 与 SQL 两套实现必须同源修改，否则列表筛得出、统计对不上；③ 只按 handle_status 判断会漏掉 Web 流程关闭的单（handle_status 仍是 0/1）。
### 【可复用结论】
状态解析先定"权威字段 > 兼容字段 > 兜底"的优先级；一份口径需要 Java 与 SQL 双实现时，把 SQL 片段作为常量放在解析器里，改一处两边生效；文本推断只取末段，不全文匹配。
### 【关联】
code：AlertOrderStatusResolver、FireAlarmOrderServiceImpl；git：680bad7（初版）、后续 handle_status=3 的 closed 细分

## 告警处理策略框架 · 2026-08-08
> 项目：消防远程值守系统
### 【类型】
架构 / 功能开发
### 【背景】
告警来源多（TCP、UDP、AEP、摄像头、规则引擎），每个来源各写一套落库与推送逻辑，字段口径不一，新增一类来源要改主流程。
### 【方案】
- 统一消息模型 `AlarmMessage`（183 行）：来源、设备、类型、等级、时间、上下文；
- 策略接口 `AlarmProcessingStrategy`（77 行）按来源处理；
- 工厂 `AlarmStrategyFactory`（144 行）按 `AlarmSourceType` 枚举路由；
- `AlarmRecordService`（255 行）统一落库与去重；`AlarmWebSocketMessage`（91 行）统一推送模型。
### 【我的角色】
独立负责：模型设计 + 策略/工厂实现 + 接入方迁移
### 【结果】
6 个文件 809 行从 0 到 1；新增来源只需加枚举 + 策略实现，不改主流程；后续 AEP、摄像头、规则引擎接入复用同一入口（09-15 统一落库重构进一步收敛到 eiot_alert_record）。
### 【踩坑 & 根因】
① 策略工厂的注册数量与枚举不一致会静默丢消息，需要启动时校验；② 策略粒度按"事件"拆会爆炸，按"来源"分就够了；③ 统一消息模型字段设计要先对齐下游（落库、推送、统计），否则策略里还得做二次转换。
### 【可复用结论】
多来源接入先定"统一消息模型 + 来源枚举"，再用策略 + 工厂路由；新增类型只扩展枚举与实现、主流程不动，是判断扩展点设计是否合格的标准。
### 【关联】
code：AlarmMessage、AlarmProcessingStrategy、AlarmStrategyFactory、AlarmSourceType、AlarmWebSocketMessage、AlarmRecordService；git：b546ccb
### 【标签】
后端 / 设计模式 / 告警 / 架构
