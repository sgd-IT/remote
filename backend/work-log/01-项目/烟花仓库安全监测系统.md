## monkey-monitor · MQTT 双链路技术摸底与设计债盘点 · 2026-10-09
> 项目：烟花仓库安全监测系统（anwei-fireworks）
### 【类型】
架构 / 技术债
### 【背景】
系统依赖 MQTT 接收现场数据（自研人员定位卡牌、温湿度液位传感器）并向青天平台闸机设备下发人员同步指令，但 MQTT 使用横跨两个配置类、一套自定义封装和多个回调，此前无人能完整讲清"为什么这么设计"；需要摸清全链路，为后续维护/改造与面试知识储备打底。
### 【方案】
以"调用点盘点 → 连接建立 → 回调线程模型 → 设计动机还原"四步完成摸底：
  ① 全项目发布调用点盘点：仅 3 处（均在 QingTianService），全部走原生 paho API；自定义封装 MQTTClient.publish 零调用（模板遗留死代码）；
  ② 还原双连接架构：sensor 连接（自定义 MQTTClient 封装）订阅 /cgw/+/data-report（人员定位 CBOR 数据）+ /device/+/data_getinfo（温湿度液位）；province 连接（原生 MqttClient Bean）以设备序列号为 topic 下发指令；
  ③ 从代码注释还原订阅侧自定义封装的三处历史故障补偿（回调重订阅 bug、多线程 publish 死锁、回调异常断连）；
  ④ 解构发布侧"MQTT 信令 + HTTP 数据"混合模式（MQTT 只通知设备去 HTTP 拉数据，大报文不走 MQTT）。
### 【我的角色】
独立负责：链路盘点、设计动机还原、复用结论沉淀
### 【结果】
产出 MQTT 双链路完整技术画像（2 条独立连接、2 个订阅主题、3 处发布点）；还原 3 处历史故障的设计补偿；沉淀 6 条可复用结论；识别 3 项设计债（publish 死代码、发布无重试补偿、连接日志明文密码）。
### 【踩坑 & 根因】
① 自定义封装 MQTTClient.publish 带"多线程死锁防护"注释却是零调用死代码 → 根因：从通用 MQTT 模板引入后业务迁移到原生 API，未清理模板代码；② 订阅主题用配置值，但 messageArrived 分发判断硬编码 topic 串 → 隐患：改配置主题会出现"订阅成功但消息不处理"的隐性故障。
### 【可复用结论】
（面试可直接展开）① MQTT 重连后必须重订阅，订阅动作应放 connectComplete 回调而非 @Bean 初始化（初始化阶段连接未就绪，订阅不可靠）；② paho 回调线程内不直接操作数据库、不抛异常，否则触发断线重连——消息处理下沉到 Spring Bean + 全量 try-catch，非 Bean 的回调类用静态容器取 Bean；③ paho 多线程 publish 会死锁，需 synchronized + waitForCompletion 超时；④ messageArrived 收到的 topic 已被 broker 展开（+ 已替换为具体值），来源识别需客户端自实现通配符匹配，paho 不提供"命中了哪个订阅"；⑤ 是否封装按痛点决定：回调线程场景需要静态可达的连接引用才封装，普通 Bean 注入场景直接用原生 API 最简；⑥ MQTT 信令 + HTTP 数据混合模式：QoS1 保同步类指令、QoS0 保删除类指令、retained=false 防过期指令重放（信令必须一次性消费）。
