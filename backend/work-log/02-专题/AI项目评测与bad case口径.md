# AI 项目评测与 bad case 口径

> 适用：RAG / 工具调用类 AI 项目（Spring AI、LangChain 等）。目的：把“跑通了”变成“可量化、可回归、可解释”。
> 用法：建黄金集 → 跑基线 → 按 bad case 分类归因 → 每次改动前后对比。01 记录里的 AI 条目必须引用本文口径。

## 一、工程档门槛（先过门槛再写简历）

评测、可靠性、成本三项至少占两项，且有真实使用场景；否则只记 01，不进 06 与简历池。

- 评测：黄金集 ≥50 条，有核心指标与前后对比，有 bad case 分类和未解决项；
- 可靠性：工具调用失败率、超时重试、人工兜底/回滚、多步任务状态持久化；
- 成本：单次调用成本、token 消耗、降本手段与月省金额；
- 真实场景：真实使用量与反馈，内部工具也算，纯 demo 不算。

## 二、黄金集字段（JSONL 与表格同构）

| 字段 | 必填 | 说明 |
|---|---|---|
| id | 是 | 唯一编号，如 RAG-001 |
| category | 是 | 事实问答 / 流程制度 / 工具调用 / 边界拒答 / 多轮 |
| question | 是 | 真实用户问法，保留口语和不完整表达 |
| expected_answer | 是 | 标准答案要点，不要求逐字 |
| must_include | 是 | 必须出现的关键点，可多条 |
| must_not_include | 否 | 禁止出现的错误结论或越权内容 |
| expected_sources | 是 | 期望命中的文档名 + 章节，用于算 Recall@K |
| tool_expected | 否 | 期望调用的工具名，空表示不应调工具 |
| tool_args_expected | 否 | 关键参数期望值，用于判参数正确性 |
| difficulty | 是 | easy / medium / hard |
| pass_criteria | 是 | 本条怎么判通过（规则或人工口径） |
| notes | 否 | 出题依据、同义问法、关联的历史 bad case |

JSONL 示例：

```json
{"id":"RAG-001","category":"事实问答","question":"……","expected_answer":"……","must_include":["……"],"must_not_include":[],"expected_sources":["XX制度.docx#第3节"],"tool_expected":null,"tool_args_expected":null,"difficulty":"easy","pass_criteria":"must_include 全覆盖且无 must_not_include","notes":""}
```

## 三、50 条配比（小项目起步够用）

| 类型 | 条数 | 说明 |
|---|---|---|
| 事实问答 | 20 | 文档里能直接找到答案，考召回与忠实度 |
| 流程/制度 | 15 | 需要跨段落归纳，考切分与重排 |
| 工具调用 | 10 | 必须调工具才能答，考工具选择与参数 |
| 边界拒答 | 5 | 知识库外或越权问题，考拒答与不编造 |

难度按 easy:medium:hard ≈ 3:4:3；同一问题可保留标准问法与口语问法，但用不同 id 计分。

## 四、指标口径

| 指标 | 口径 | 起步目标 |
|---|---|---|
| 答案正确率 | 通过条数 / 总条数，按 pass_criteria 判定 | ≥80% |
| 检索 Recall@5 | expected_sources 出现在 Top5 的比例 | ≥85% |
| 引用正确率 | 答案引用来源与 expected_sources 一致的比例 | ≥90% |
| 工具选择正确率 | tool_expected 与实际调用一致的比例 | ≥90% |
| 工具参数正确率 | 关键参数与 tool_args_expected 一致的比例 | ≥85% |
| 工具调用成功率 | 无异常/超时且结果被正确使用的比例 | ≥95% |
| 拒答正确率 | 边界题正确拒答、非边界题不误拒的比例 | ≥90% |
| P95 延迟 | 端到端耗时 P95（流式另记首 token 延迟） | 按场景定 |
| 单次成本 | 输入 token × 单价 + 输出 token × 单价 | 记录基线后降 30% |

每次改动的报告至少包含：版本、改动点、上述指标、bad case 数量变化。

## 五、bad case 分类口径

| 编码 | 类型 | 判定标准 | 典型现象 | 优先修复方向 |
|---|---|---|---|---|
| R1 | 知识缺失 | 文档里确实没有答案 | 模型只能编或答“不知道” | 补文档，不要改提示词硬编 |
| R2 | 切分/表述不匹配 | 文档有答案但召回不到 | 换个问法就能答对 | 调切分粒度、加同义问法、换 embedding |
| R3 | 排序靠后 | 召回有但不在 TopK | Top10 有、Top3 没有 | 加重排、调 TopK |
| G1 | 幻觉 | 答案含无依据结论 | 编造数字或条款 | 收紧提示词、强制引用、降温度 |
| G2 | 引用不符 | 引用来源与答案不匹配 | 答对了但引错文档 | 引用与答案按句绑定校验 |
| G3 | 要点遗漏 | must_include 未覆盖 | 答一半 | 提示词列要点、拆多轮 |
| T1 | 工具选择错误 | 该调没调或不该调乱调 | 知识问答却去查库 | 工具描述写清边界，加路由 |
| T2 | 工具参数错误 | 参数缺失/类型错/值错 | 查错人、查错时间 | 参数 schema + 校验 + 示例 |
| T3 | 工具失败未兜底 | 异常或超时直接失败 | 报错或空回答 | 重试 + 幂等键 + 人工兜底 |
| T4 | 工具结果未回填 | 调了但答案没用结果 | 答非所问 | 固定“调用→解析→回填”流程 |
| C1 | 多轮上下文丢失 | 指代或前文条件丢失 | 第二轮答错对象 | 保留会话状态、显式摘要 |
| B1 | 该拒答没拒答 | 知识外或越权仍回答 | 编造制度条款 | 加拒答规则与权限校验 |
| B2 | 不该拒答却拒答 | 有答案却拒答 | 过于保守 | 放宽阈值、补召回 |
| P1 | 格式不达标 | JSON/字段/引用格式错 | 解析失败 | 输出 schema + 解析失败重试 |
| L1 | 延迟/成本超限 | 超过阈值 | 首 token 慢、token 爆炸 | 上下文压缩、缓存、小模型路由 |

归类规则：一条 case 只记主因编码；同时命中多个时，按“检索 → 生成 → 工具 → 兜底”的顺序取最上游。

## 六、单条评测记录字段

| 字段 | 说明 |
|---|---|
| case_id / run_id | 用例编号 + 本次运行编号 |
| retrieved_docs | TopK 文档与分数，用于判断 R1/R2/R3 |
| answer | 实际输出，保留原文 |
| tool_calls | 工具名、参数、返回、耗时 |
| verdict | pass / fail |
| badcase_code | 上表编码 |
| root_cause | 一句话根因，不写“模型不行”这种废话 |
| fix | 本次改了什么；没改就写“待修” |
| cost / latency | 本次 token、费用、耗时 |

## 七、执行节奏

1. 基线：先跑 50 条，不调参，记录真实水平；
2. 归因：按编码统计分布，找出占比最高的两类；
3. 改动：一次只改一个变量（切分/提示词/模型/工具 schema），再跑同一套；
4. 对比：报告“指标 + bad case 分布”的前后变化；
5. 收敛：未解决项写进 01 的【施工】【待办】，达标后再升级 06/简历池。

## 八、出题与填表指引（50 条模板配套）

模板文件：`02-专题/AI评测黄金集-50条模板.csv`（UTF-8，Excel 打开如乱码则用“数据 → 从文本/CSV 导入”选 UTF-8）。

- 多值字段用 `|` 分隔：`must_include`、`must_not_include`、`expected_sources`；代码读取时 `split('|')`。
- 工具题的 `tool_args_expected` 只写关键参数，格式 `参数名=值`，多个用 `|` 分隔。
- 空值统一留空字符串，不要写“无”“N/A”，避免统计口径不一致。

### 出题顺序

1. 从真实使用里收集 10 个问题（自己用、同事问、文档里最容易问的），不要先编；
2. 按五类扩到 50 条：事实问答 20、流程制度 15、工具调用 10、边界拒答 5；
3. 每条标 `expected_sources`，标不出来说明这题不该进黄金集；
4. 最后补难度：单段直接命中 = easy，跨段归纳 = medium，多步工具/歧义/多文档 = hard。

### 出题原则

- 用真实问法：保留口语、省略、错别字、指代（如“这个多久能到账”），不要把所有题写成书面语；
- 事实题和流程题必须能在文档里找到依据，找不到的移到边界拒答；
- `must_include` 写 2–4 个可判定的短语，不要写“回答准确”这种无法判定的描述；
- `must_not_include` 只写必须禁止的内容：错误数字、越权数据、编造条款；
- 工具题必须写清 `tool_expected` 和关键参数；不需要调工具的题，`tool_expected` 留空；
- 边界题要真的越权或知识库外，不要用“文档里没写清楚”的题凑数；
- 同一问题最多保留 2 种问法（标准 + 口语），且用不同 id，避免重复计分。

### 自检清单（填完 50 条后逐项打勾）

- [ ] 五类配比符合 20/15/10/5，难度接近 3:4:3；
- [ ] 每条有唯一 id，且 id 与分类连续；
- [ ] 事实题和流程题都能在 `expected_sources` 定位到原文；
- [ ] 每条 `must_include` 都能在答案里明确判定“有/没有”；
- [ ] 工具题都有 `tool_expected`，关键参数具体到值；
- [ ] 边界题都能说清“为什么不该答”；
- [ ] 至少有 10 条口语问法，不是全书面语；
- [ ] 没有同一问题重复 3 次以上；
- [ ] `notes` 已清空“待填”，或写明来源。

### 跑完基线后

用第六节字段记录每次运行；至少产出：答案正确率、Recall@5、工具调用成功率、P95 延迟、单次成本。把结果和 bad case 分布写回 01 记录的【评测与成本】和【施工】【待办】。
