# project-map 项目地图

为任何项目建立"人机共用"的地图，让改动可定位、决策可追溯、审计权留在人手里。

核心公式：**地图 = 最小约束集 + 入口索引 + 决策日志**。

使用本 skill 时，输出开头标注【项目名·project-map】，项目名取当前工作区根目录名（如 hc-standard、remote-monitor）。

## 三条铁律

1. **可推导信息不落盘**——目录结构、调用关系、依赖图随时现场扫；只有四类不可推导信息值得持久化：约束（禁令）、决策（why）、契约（跨端约定）、索引（入口）。
2. **先盘点再产出**——先清点既有文档资产（README / ARCHITECTURE / docs / specs / ADR …），能引用不重造，能修复不重写；文档漂移（引用失效）本身就是产出素材。
3. **落盘前确认**——所有文件创建/修改先列清单，经用户确认后执行；Git 边界见下。

## Git 边界（硬性）

- 全程 git 只读（log / diff / status / show），**禁止任何 git 写命令**（add / commit / push / stash / reset / checkout）。
- 产出文件一律留在工作区未提交状态；是否提交、何时提交，由用户决定。
- skill 本体位于用户级目录（不在任何 git 仓库内），不创建项目级副本，避免随仓库提交给他人。

## 模式判定

| 模式 | 触发 |
|---|---|
| 建图模式（默认） | 进入/接手项目；用户说"了解这个项目""没有项目地图""梳理架构""onboarding" |
| 更新模式 | 用户说"更新项目地图""刷新地图" |

## 建图模式流程

### 第 1 步：盘点（只读）

先确认工作区形态（单仓 / 多仓 / 根目录是否 git 仓库 / 辅助目录与空目录残留），再并行采集：

| 盘点项 | 采集方法 |
|---|---|
| 仓库边界 | 顶层目录结构；识别 .git 归属；标注空目录、残留目录、第三方目录 |
| 技术栈 | 各仓清单文件：package.json / pom.xml / go.mod / pyproject.toml / requirements.txt |
| 入口与配置 | 启动类、application*.yaml、.env*、路由注册文件、端口、代理配置 |
| 既有文档资产 | `**/*.md` 与 docs/、doc/、specs/、plans/、adr/ 目录；重点找架构、集成契约、设计文档、决策记录 |
| 业务域分布 | 后端 Controller / 路由目录、前端 views / pages，按业务域归类 |
| 文档漂移 | 抽查既有文档引用的路径是否存在；失效引用单独记录 |
| 规模预警 | 统计或抽样文件行数，列出"巨型文件"，提醒后续只读关键段 |

纪律：用语义搜索 + 目录列举定向采集，不通读全仓；大文件只读关键段落；配置文件中只记录"凭据在哪个文件"，绝不抄录密钥值。

### 第 2 步：输出对话版地图（先在对话交付，不落盘）

固定 6 段，语言跟随用户：

1. **系统全景图**：ASCII ≤15 行——各端 → 接口/协议（附端口） → 服务 → 存储与第三方
2. **各仓/模块结构**：技术栈、模块职责表、请求链路、关键配置位置
3. **业务域 × 端 速查表**：业务域 → 后端入口 → 前端页面 → API 文件 → 其他端
4. **"我要做 X → 改哪里"表**：最高频查询，必须产出（覆盖改接口 / 改页面 / 联调 / 查数据）
5. **既有文档索引**：比地图更细的文档链接，按"先读哪个"排序
6. **已知坑**：文档漂移、易混点、巨型文件、契约暗号（如成功码约定）

### 第 3 步：确认后落盘（默认最小集，按性价比排序）

先列清单（目标路径 + 一句话内容）给用户确认，再创建：

1. **每仓根 AGENTS.md**（<40 行）：硬禁令 + 常用命令 + 文档索引指针 + 更新触发器
2. **docs/INDEX.md**：第 2 步的 3/4/6 段持久化（业务域表 + 改哪里表 + 已知坑）
3. **既有 specs/plans/设计文档目录的索引页**（存在时）：每篇一句话摘要
4. **追溯性 ADR ×3**：挑"奇怪但有意为之"的代码补 why（先和用户确认哪些是死守的）
5. **图**：仅 1 张核心链路 Mermaid 时序图 + 1 张稳定层架构图；ER 图链接既有 DB 文档，不重画

落位约定：优先放进仓库既有文档目录；无惯例时用 docs/。多仓工作区：AGENTS.md 放各仓根，INDEX.md 放主仓或用户指定位置。

每个落盘文件末尾必须有"更新触发器"小节：写明什么变更必须同步此文件。

### 第 4 步：验证

- [ ] 文件内引用的路径逐个复核存在（重新 Glob）
- [ ] 无任何密钥/凭据被抄录
- [ ] AGENTS.md < 40 行；INDEX.md 可 30 秒扫完
- [ ] 30 秒自测：随机挑 2 个功能问"改哪里"，查表能定位
- [ ] git status 改动清单与落盘清单一致，且全部未提交

## 更新模式流程

1. 读既有产物（AGENTS.md / INDEX.md / ADR），提取它们声称的事实：模块、入口、端口、路径。
2. 对现状做只读 diff：目录结构、路由、Controller/页面、端口、依赖清单、文档漂移。
3. 输出差异清单：失效引用 / 新增未收录 / 相互矛盾，逐条给处理建议。
4. 经确认更新文件，并刷新"最后核实"标注。
5. 更新后走第 4 步验证。

## 反模式（禁止）

- ❌ 通读全仓再输出；❌ 大文件整读
- ❌ 把调用图 / 依赖图 / 完整目录树制成大文档提交（可推导、腐烂快）
- ❌ 给所有模块批量建 README（只写用户点名的核心域卡片）
- ❌ 未经确认在仓库创建文件；❌ 任何 git 写操作
- ❌ 抄录配置文件中的密码 / 密钥 / appSecret
- ❌ 只输出对话版就宣称完成（用户要求落盘时必须走第 3 步）
- ❌ 落盘文档写死易过期的版本号 / 日期（或标注核实日期）
- ❌ 重复造轮子：既有文档能覆盖的只做链接
