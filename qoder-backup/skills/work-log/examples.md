# 填写示例

本文件是 [SKILL.md](SKILL.md) 的补充资料，展示各类记录的填写范式。

## 示例 1：完整单条记录（模板填法示范）

```markdown
【日期】2026-09-21
【项目/模块】订单中心 — 超时未支付自动关单
【类型】性能优化 / 重构
【背景】原方案每分钟全表扫描未支付订单，日约 300 万次无效查询，订单表 CPU 峰值 78%，大促前存在漏单风险
【方案】用 Redis ZSET 延迟队列替代轮询：下单时写入带到期时间戳的 ZSET，消费者按到期扫描关单；选 ZSET 而非 MQ 延迟消息的原因：需要支持取消订单时移除任务（ZREM）
【我的角色】主导：方案设计 + 核心编码 + 灰度上线
【结果】消除每日约 300 万次无效查询；订单表 CPU 峰值 78% → 22%；支撑日均 40 万单无漏单
【踩坑 & 根因】现象：灰度期间偶发"已支付订单被关单" → 定位：支付回调与关单消费者并发竞争 → 根因：关单前未二次校验订单状态，且未加分布式锁
【可复用结论】延迟队列消费端必须"取任务后二次校验业务状态"，不要假设任务取出时条件仍成立
【关联】commit a1b2c3d；MR #128
【标签】后端 / Redis / 性能优化 / 订单
```

## 示例 3：本项目真实工作改写（消防远程值守系统）

> 基于大屏告警弹窗去重工作；结果数字用占位符，记录时应补真实值。

```markdown
【日期】2026-09-29
【项目/模块】值守大屏 — 报警弹窗去重
【类型】故障排查
【背景】大屏告警弹窗同一告警反复弹出，干扰值守人员处置
【方案】梳理告警推送链路，确认轮询与推送两条路径各自触发弹窗；在弹窗队列入口按告警唯一标识去重，保留最新一条
【我的角色】独立负责：根因定位 + 方案设计 + 前后端落地
【结果】重复弹窗消除（补真实数据：弹窗量从日均 A 次降至 B 次）
【踩坑 & 根因】现象：同一告警短时间弹多次 → 定位：多个触发源各自入队 → 根因：弹窗队列缺幂等去重，且上游无法保证只推一次
【可复用结论】任何"实时弹出/提醒"类需求，先定唯一键并在消费端幂等去重，不能依赖上游只推一次
【关联】对应 commit 链接（补真实值）
【标签】前端 / WebSocket / 线上故障 / 告警
```
