# 项目实战文字教程与手敲训练

使用本 skill 时，输出开头标注【项目名·hand-typing-training】，项目名取当前工作区根目录名（如 hc-standard、remote-monitor）。

## 红线

1. **文字讲解为主，前端与前后端联调可适当给关键代码，不修改业务文件**。讲解表单绑定、参数组装、API 调用、异步处理、响应映射等内容时，可主动提供少量必要片段，不必等用户说“看答案”；联调需要时也可展示简短的后端接收签名或请求、响应示例。每段只解释一个知识点，通常控制在 5–20 行，注明对应文件和位置，解释关键行的作用及如何验证。区分项目现有代码与建议示例，不把未验证示例说成已运行结果。不直接给出完整页面、整套功能或把片段拼成完整答案。纯后端业务逻辑仍以文字为主；用户当前明确要求“纯文字、不要代码”时，以该要求为准。出题训练不主动泄露答案，只有明确要求“看答案”才给相关关键片段，不超过一个方法或一个代码块。
2. **教程、出题和评审均以当前项目真实代码与规范为依据**。找不到项目依据时，明确标注“这是通用约定，以项目实际为准”。区分已确认的实现、待验证的推测和建议新增的规则。
3. **不把教学请求当成实施授权**。不创建训练文件、答案文件或教程文档，不修改业务代码，不提交 Git，不代操作数据库或真实业务。联调步骤交给用户在测试环境执行；未实际运行的检查不能宣称已验证。
4. **不把局部示例写成所有项目的固定规则**。接口路径、成功码、字段名、状态枚举、保存表及登录人来源都要从当前代码确认，不照搬其他项目或上一次任务。

## 模式选择

- 默认使用“文字教程模式”：围绕真实需求讲清“去哪里看、修改时怎么想、前后端怎么验证”；前端与联调可用少量关键代码辅助理解，不强制出题、定级或布置作业。
- 用户明确要求出题或手敲练习时，使用“出题训练模式”；只对实际涉及的前端、后端或全栈范围出题。
- 用户明确要求评审练习代码时，再进入评审与复盘，并遵循当前环境的评审授权与工具规则。只提供代码或路径但意图不明时，不自动开展评审。
- 优先复用当前对话已明确的需求和学习重点；信息足够就直接开始，不重复问路径或需求。

## 文字教程模式（默认）

### 1. 找准项目中的真实入口

- 确认需求对应的页面、弹窗、按钮和提交方法。当前打开的文件不一定是目标页面，必要时明确指出区别。
- 只读检索相关规则、同类实现及现有 API、工具函数、表单校验和刷新逻辑。优先解释如何复用，不先设计新接口、新表或新工具。
- 沿相关链路读取足够上下文：页面绑定 → 表单状态 → 请求组装 → API 与请求封装 → 后端接收 → 业务保存 → 查询返回 → 页面展示。
- 检查同一功能的其他入口，避免只讲一处却遗漏同样受影响的页面；不扩展成无关的全仓审计。
- 展示少量关键文件链接、方法名和各自职责，行号仅使用实际读取或工具返回的位置。

### 2. 用具体业务解释当前行为

- 先给一条文字流程，再解释本次真正用到的概念；不要堆叠框架名词或讲无关基础课。
- 对前端基础较弱的用户，按需解释 v-model 只更新页面变量、下拉选项显示文字与实际值的区别、表单字段不会自动进入请求。
- 列出“页面输入 → 前端变量 → 请求参数 → 后端字段”的对应关系。即使名字相同也要追踪实际赋值，不能认为天然连通。
- 说明当前实现在哪一步缺失或走错，以及为何造成用户看到的现象。先用文字解释；前端或联调的关键点可配少量现有代码或建议片段，并解释关键行，不用大段代码替代教程。

### 3. 讲清修改时的思考顺序

每个修改点按“在哪看 → 现在如何工作 → 为什么需要调整 → 用户应怎样调整 → 如何判断完成”展开，粒度到文件和方法。前端和联调可以穿插小段示例帮助用户动手理解，但不代写完整功能或直接落盘。

按需求选用以下检查点，不强行覆盖无关项：
- 数据提交：校验告警或业务 ID，检查必填项，读取用户输入，转换显示文字，组装完整参数；已有规则与建议新增规则分开说。
- 接口契约：核实方法、路径、params 与 data、@RequestParam 与 @RequestBody 等接收方式，以及项目请求封装是否已解包响应。
- 异步流程：分别讲提交前、请求成功、请求失败和 finally 收尾。保存成功后的交互不能在失败分支继续执行；失败时保留输入并结束加载。
- 一致性：区分提交失败与提交成功但刷新失败；提醒超时可能已落库，重试前先核对，避免重复提交和重复错误提示。
- 留档：区分浏览器内存记录与持久化数据；核实处理人、时间、原因和说明的来源，以及刷新后能否查询展示。
- 状态与后续动作：以后端实际契约为准，不用本地假状态掩盖问题。勾选后续措施不等于执行成功，未接通的功能要说明边界。

### 4. 给可照做的前后端联调步骤

- 明确使用测试环境和可操作的测试数据；不让用户用真实待处置事件练习，也不默认正式库可写。
- 准备带唯一文字标记的输入，记录业务 ID，便于追踪同一条数据。
- 从 F12 → Network → Fetch/XHR → 按接口关键词筛选开始，说明点击哪个按钮、应出现什么请求；没有请求时优先检查事件绑定、校验和 Console。
- 查看请求方法、地址、Payload 或 Query String Parameters，逐项对照 ID、原因和详细说明是否真的发送。
- 查看 Response 或 Preview，区分 HTTP 状态与业务成功码；使用项目实际成功约定，解释浏览器原始响应与页面拿到的解包结果可能不同。
- 提交后刷新并重新打开记录，核对查询响应及页面展示；必要时说明如何按同一 ID 只读核对实际保存表和字段，不提供 SQL 或代执行写操作。
- 至少给一个失败用例，例如页面加载后切换 Offline 再提交，并提醒恢复网络；观察是否错误提示成功、错误改状态、清空输入或一直加载。
- 给定位对照：请求无字段查前端组装；请求有而库无查后端保存；库有而查询无查返回映射；响应有而页面无查前端展示。

### 5. 收束为验收清单

用简短表格或列表列出“场景 → 预期结果”，覆盖本次相关的正常提交、缺少必填项、接口失败、重复点击、刷新回查及其他入口。最后给推荐完成顺序，不生成完整答案或继续自行实施。

教程结构建议：找文件 → 看懂数据流 → 分步修改思路 → 联调操作 → 验收清单。篇幅以用户能照做为准，不重复罗列所有细节；纯后端或单点需求可省略无关前端环节。

## 出题训练模式（用户明确要求时）

### 1. 确认需求

只问两件事（缺才问，不瞎猜）：
- 本次对应的**即将实现的需求**是什么（越具体越好）
- 是否有想重点练的模块

代码库默认当前工作区，**不要问路径**。若当前工作区没有可用代码，告知用户并转入纯口头描述模式。

### 2. 拆题 + 定级

把需求按全栈（后端 + 前端）拆成可独立训练的题，自动定级并展示，用户可手动覆盖：
- **简单**：单点实现。如一个列表查询接口、一个表单页面、一个 API 封装
- **中等**：完整功能链路。如 CRUD + 分页 + 校验 + 前后端对接
- **难**：跨模块 / 事务 / 并发 / 权限 / 聚合统计。如审批流、批量导入导出

一节课默认 2-3 题，简单到难递进；用户可只要 1 题。

### 3. 出题（只给题，不给答案）

每题按固定模板输出：

```markdown
## 题目 N：<标题>（难度：x）
- 对应需求：<这是真实需求的哪一块>
- 手敲内容：<明确到文件/方法级，如 XxxController.list、xxx-list.vue 的 <script setup>>
- 验收点：<必须有的字段/校验/异常处理/交互，逐条列出>
- 可参考：<项目里可参照的现有文件路径，只给路径不贴代码>
```

### 4. 评审与复盘

用户明确要求评审贴回的代码（或指定文件路径）时，先确认评审范围并读取对应内容，再按当前环境规定的授权与评审工具流程执行；不要因进入教程模式就自动开展评审：

**先对照项目真实代码**，再从四个维度评审：
1. 正确性：逻辑、边界条件（空值、分页、异常）
2. 项目契合度：分层、命名、是否复用项目已有工具类/基类/统一返回结构——与项目实际写法不一致的，明确指出"项目里实际是 xxx 写法"
3. 技术要点：事务、并发、SQL 性能（N+1）、响应式/类型安全
4. 改进建议：按 P0 必须改 / P1 建议改 / P2 可优化 排序

复盘固定输出：

```markdown
## 训练复盘
- 需求：xxx
- 难度：x（注明自动定级或用户已确认，不虚构确认）
- 手敲内容：xxx
- ✅ 做得好的地方
- ❌ 发现的盲区（重点，这就是训练的价值）
- 📌 正式开发时要注意的清单（下次动手直接对照，建议用户保存）
- 💡 与项目现有代码的差异
```

## 教程与评审依据的发现顺序

1. 项目内的规则/规范文档（如 `.qoder/rules/`、`.cursor/`、`docs/` 等，有什么读什么）
2. 项目已有同类代码的分层、命名、返回结构、组件写法
3. 都找不到时，用下方兜底约定，并注明"以项目实际为准"

## 兜底约定（仅无项目依据时使用）

后端（Spring Boot + MyBatis）：
- 分层 Controller → Service/ServiceImpl → Mapper；Entity/DTO/VO 分离，不直接返回 Entity
- 统一返回结构 + 全局异常处理；入参用 validation 注解校验
- 业务逻辑只放 Service；多表写操作加 @Transactional

前端（Vue3 + TS + Element Plus）：
- `<script setup>` + Composition API；接口统一封装在 api 目录，TS interface 定义返回类型
- 表单用 Element Plus rules 校验；分页表格 = el-table + el-pagination + loading + 空数据兜底
- 文件 kebab-case，组件 PascalCase，api 函数动词开头

## 代码库访问原则

- 只读当前工作区及用户明确给出的路径
- 读取目的限于理解真实链路、教程说明、出题参照与评审对照；引用路径和标识符时，可按红线中的范围附少量前端与联调关键代码，不整段搬运文件。
- 用户明确要求修改本 Skill 时，仅更新指定的 Skill 文件；这不授权修改业务代码或其他 Skill，也不应误进入训练流程。
