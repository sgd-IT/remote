# 决策点驱动编码（Decision-Driven Coding）

用动态决策点激活深度思考：先写决策注释（业务语言），再手写代码，AI 仅做决策校验。

使用本 skill 时，输出开头标注【项目名·decision-driven-coding】，项目名取当前工作区根目录名（如 hc-standard、remote-monitor）。

## 何时使用

- 业务核心逻辑开发（单文件决策点 ≤3 个；非核心代码如 DTO 直接跳过）
- 技术组件选型、技术方案设计
- 核心链路兜底逻辑、性能优化、重构

## 每日训练节奏（固定时间点）

用户每天进行两次训练，到点或被提醒时按对应流程执行：

### 早间训练 9:30（编码启动，约5分钟）

1. 确定今日核心任务，选 1 个动态引擎运行
2. 关闭 AI 代码生成，手写 3 个决策点到目标文件顶部
3. 卡住时自问："如果线上出问题，我能向 CTO 解释为什么这样设计吗？"
4. 用 STEP 2 模板让 AI 仅校验决策逻辑，随后手写代码并锚定 DP-X

### 收工训练 18:00（下班前复盘，约5分钟）

1. 执行下方"每日健康度检查"全部 4 项
2. 核对今日提交的每个 `[决策锚点]` 是否关联具体证据ID，Commit Message 是否符合规范
3. 由 Qoder 统计并记录：今日手写行数 / 当日总新增代码行数，计算手写占比，最终目标 ≥10%（统计方式：`git diff --stat` 当日新增总行数 vs 手写部分行数，以决策锚点段落及用户确认为准）
4. 今日决策点不达标的，当场重写或补证据，不带病过夜

## 三个动态决策点生成引擎

根据当日任务类型选 1 个引擎运行，编码前手写 3 个决策点到代码文件顶部。

### 引擎1：风险倒逼生成器（业务逻辑代码首选）

自问：**"如果这段代码明天凌晨2点炸了，最可能因______？且该问题______无法被监控告警捕获"**

```java
/**
 * [决策点] 为何______？
 *   - 风险：______（监控盲区：______）
 *   - 防御：______（证据：______）
 */
```

### 引擎2：知识盲区扫描器（技术组件选型必备）

自问：**"这段代码里，我最不敢向架构师解释的部分是______？因为______"**

```java
/**
 * [决策点] 为何______？
 *   - 盲区突破：______（证据：______）
 *   - 验证：______
 */
```

### 引擎3：极端场景压力器（核心链路兜底）

自问：**"如果______（不符合需求但可能发生），现有设计会______，因为______"**

```java
/**
 * [决策点] 为何______？
 *   - 压力场景：______（证据：______）
 *   - 权衡：______
 */
```

## 操作流程（5分钟启动编码）

### STEP 1：动态生成决策点（编码前必做）

硬性规则：
- 每个决策点 ≤3 行（超限 = 问题拆解不足）
- 证据必须可追溯（文档ID / 监控ID / 测试报告 / 历史故障编号），禁止模糊表述
- 结合项目上下文：优先关联项目特定证据（需求ID、故障编号、压测报告）

### STEP 2：仅用 AI 验证决策逻辑（禁止让 AI 生成代码）

提问模板：

```text
我计划[简述决策]，依据是：
1) [证据1]
2) [证据2]
但担心[具体风险]。
请分析：
- 该决策的漏洞（需给出技术细节）
- 可落地的监控/防御方案（需含具体阈值）
```

AI 输出应仅包含：决策漏洞分析 + 可落地监控方案（如"锁等待时间 P99>200ms 告警"）。

### STEP 3：手写代码时锚定决策

在关键逻辑处（方法入口、条件分支、异常处理）添加锚点注释：

```java
// [决策锚点] DP-X（风险：______，防御：______）
```

- 锚点编号 DP-X 必须与文件顶部决策点、Commit Message 一一对应
- 括号内标注关键风险和防御措施

## 结合项目代码定位决策点区域

1. 明确任务类型：新功能 / bug修复 / 性能优化 / 重构
2. 定位关键模块：需求文档标注的"关键路径"或"高风险点"、技术债文档、历史故障模块、SonarQube 高复杂度方法或循环依赖
3. 结合项目文档与评审记录预判风险点和知识盲区，运行对应引擎生成决策点并嵌入代码锚点

## Commit Message 规范

```text
feat(order): 实现缓存穿透防护（决策点：DP-1/2）
- DP-1: ConcurrentHashMap依据：MON-2024-07-10监控
- DP-2: 空值TTL=5min依据：需求文档§3.2 + 防御缓存池爆炸
- 风险: 需监控缓存池容量>80%告警（已加Config.CACHE_POOL_LIMIT）
```

## 每日健康度检查（收工前1分钟）

| 检查项 | 达标标志 | 未达标时行动 |
| ------ |------ |------ |
| 是否引发后背发凉感？ | 生成时手心出汗/心跳加速 | 重新运行生成器，直到找到真风险 |
| 能否用1句话向产品解释？ | 产品说"原来这里会炸！那加个运营审批吧" | 重写决策点，剔除技术黑话 |
| 3个月后还能看懂吗？ | git show 历史决策点能复现当时场景 | 补充具体事件ID（如"2024-07-15运营事故"） |
| 决策点是否关联项目上下文？ | 含项目特定证据（需求ID/故障编号） | 补充缺失上下文或拆分不相关决策 |

## 证据缺失时的兜底

- 监控数据缺失 → 立即补监控（例：`monitor.addAlert("lock_wait_time", P99>200ms)`）
- 文档未定义 → 用 `// [待确认]` 标注，提交时自动创建跟进任务（Jira）
