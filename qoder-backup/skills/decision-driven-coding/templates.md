# 决策点驱动编码 - 模板、CI 检查与 FAQ

## 项目代码决策点模板（快速参考）

```markdown
# 项目模块：XXX（如订单处理）
## 决策点列表
### [决策点] XXX
- **风险/盲区**：XXX
- **防御/选择**：XXX
- **证据**：XXX（需求ID/故障编号/测试报告）
- **代码锚点**：`src/module/XXX.java:LINE-NUM`
```

## CI 流水线检查（防止决策点流于形式）

```bash
# 检查代码是否包含决策锚点
grep -r "\[决策锚点\]" src/ || exit 1
# 检查决策点是否含证据ID
grep -r "证据：" src/ | grep -v "ID:" && echo "Missing evidence ID!" && exit 1
```

## 团队协作规范

1. 在团队编码规范中明确决策点注释格式（必须使用 `[决策点]` / `[决策锚点]` 标签）
2. 通过 Code Review 强制要求关键逻辑包含决策点
3. 定期组织"决策点复盘会"，讲解核心决策逻辑及其背后的项目考量

## 常见问题解答

### Q：决策点太多会拖慢开发速度？

只针对核心逻辑生成决策点（单文件 ≤3 个）。非核心代码（如 DTO）直接跳过。

### Q：证据找不到怎么办？

- 监控数据缺失 → 立即补监控（例：`monitor.addAlert("lock_wait_time", P99>200ms)`）
- 文档未定义 → 用 `// [待确认]` 标注，提交时自动创建 Jira 任务

### Q：如何避免决策点流于形式？

在 CI 流水线加入上文检查脚本，并配合每日健康度检查（见 SKILL.md）。

### Q：在现有项目中，如何快速定位需要生成决策点的代码区域？

1. 查看项目技术债文档或历史故障记录，优先处理高风险模块
2. 使用代码分析工具（如 SonarQube）识别复杂度高的方法或循环依赖
3. 针对新需求，聚焦需求文档中明确标注的"关键路径"或"高风险点"

### Q：团队协作时，如何确保其他成员理解决策点注释？

见上文"团队协作规范"三条：统一格式、Review 强制、定期复盘。

## 今日行动清单

1. **下次写核心逻辑前**：关闭 AI → 运行 1 个动态引擎 → 手写决策点到文件顶部
2. **卡住时自问**："如果线上出问题，我能向 CTO 解释为什么这样设计吗？"
3. **提交代码时**：检查每个 `[决策锚点]` 是否关联到具体证据ID，用规范 Commit Message 提交
4. **当想让 AI 生成代码时**：先手写决策点 → 把问题发给 AI → 只复制 AI 的决策分析
5. **在现有项目中**：选取一个功能模块（如支付流程、用户注册），分析风险点，生成至少 2 个决策点并嵌入关键代码处，PR 中说明决策点编号及证据
6. **学习他人项目**：阅读开源项目代码时，尝试逆向推导其决策点（为何选择某技术组件？如何防御某风险？）

## 自我承诺决策点（首个实践）

```text
[决策点] 为何今日实施本技能？
  - 风险：手写能力退化导致技术判断力丧失（证据：上周3次AI生成代码引发线上故障）
  - 验证：手写行数占当日总新增代码行数比例最终达到10%（由Qoder每日统计记录）
```

真正的编码能力不是记住语法，而是让每一行代码都带着"为什么"的烙印。
